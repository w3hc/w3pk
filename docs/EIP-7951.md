# EIP-7951: Account Abstraction via P-256 Passkeys

## Overview

EIP-7951 enables Ethereum accounts to use WebAuthn passkeys (P-256 curve) for signing instead of traditional secp256k1 private keys. This allows for:

- **Native passkey support** - No seed phrases or private key management
- **Hardware-backed security** - Signatures generated in secure enclaves (Secure Enclave, TPM)
- **Account abstraction** - Smart contract wallets that verify WebAuthn signatures on-chain
- **Biometric authentication** - Face ID, Touch ID, Windows Hello, etc.

w3pk implements EIP-7951 PRIMARY mode through a [P-256 smart account](#primary-smart-account) the passkey owns: `signMessage()` in PRIMARY mode signs as that account, and `sendTransaction()` sends ERC-4337 UserOperations from it.

### Key Components

#### 1. Message Signing with Passkeys

`signMessage()` in PRIMARY mode signs EIP-191, SIWE and EIP-712 messages with the passkey, as the account (see [Signing Messages](#signing-messages)):

```typescript
const result = await w3pk.signMessage("Hello World", { mode: 'PRIMARY', chainId: 1 })

// Result contains:
// - signature   - ERC-7739 signature, ERC-6492-wrapped while the account isn't deployed
// - address     - the passkey's smart account for the tag
// - mode, tag, origin
```

**Important Differences from secp256k1:**

| Aspect | secp256k1 (Standard) | P-256 (EIP-7951) |
|--------|---------------------|------------------|
| Curve | secp256k1 | P-256 (NIST) |
| Private Key Source | BIP39 mnemonic | WebAuthn credential |
| Signature Format | 65 bytes (r,s,v) | DER-encoded → (r,s) |
| Hash Signed | message hash | authenticatorData ‖ clientDataHash |
| Address Derivation | keccak256(secp256k1 pubkey) | CREATE2 address of the [smart account](#primary-smart-account) |

#### 2. P-256 Address Derivation (EIP-7951)

`deriveAddressFromP256PublicKey()` derives `keccak256(x ‖ y)` from a P-256 public key. No key controls it, so it isn't the `PRIMARY` address: that is the [smart account](#primary-smart-account)'s.

```typescript
// Internal implementation
export async function deriveAddressFromP256PublicKey(
  publicKeySpki: string  // base64url-encoded SPKI format
): Promise<string> {
  // 1. Import P-256 public key
  const publicKey = await crypto.subtle.importKey(
    "spki",
    base64UrlToArrayBuffer(publicKeySpki),
    { name: "ECDSA", namedCurve: "P-256" },
    true,
    ["verify"]
  )

  // 2. Export as JWK to get x and y coordinates
  const jwk = await crypto.subtle.exportKey("jwk", publicKey)

  // 3. Create uncompressed public key (64 bytes: x || y)
  const uncompressedKey = new Uint8Array(64)
  uncompressedKey.set(base64UrlToArrayBuffer(jwk.x), 0)   // 32 bytes
  uncompressedKey.set(base64UrlToArrayBuffer(jwk.y), 32)  // 32 bytes

  // 4. Hash with keccak256
  const hash = keccak256(uncompressedKey)

  // 5. Take last 20 bytes as address
  return '0x' + hash.slice(-40)
}
```

This follows the same pattern as secp256k1 address derivation but uses P-256 public key coordinates.

#### 3. DER Signature Parsing with Low-s Normalization

WebAuthn returns signatures in DER format. The `extractRS()` utility extracts r and s components and applies low-s normalization:

```typescript
export function extractRS(derSignature: Uint8Array): { r: string; s: string } {
  // Parse DER format:
  // 0x30 [total-length] 0x02 [r-length] [r-bytes] 0x02 [s-length] [s-bytes]

  // Extract r and s, handling padding
  // Pad to 32 bytes each

  // Apply low-s normalization for P-256
  const n = BigInt('0xFFFFFFFF00000000FFFFFFFFFFFFFFFFBCE6FAADA7179E84F3B9CAC2FC632551')
  let sBigInt = // ... parse s

  if (sBigInt > n / 2n) {
    sBigInt = n - sBigInt  // Normalize to low-s
  }

  return {
    r: '0x' + rHex,
    s: '0x' + sBigInt.toString(16).padStart(64, '0')
  }
}
```

**Why Low-s Normalization?**

Ethereum requires low-s values to prevent signature malleability. For P-256, we use the curve order:
```
n = 0xFFFFFFFF00000000FFFFFFFFFFFFFFFFBCE6FAADA7179E84F3B9CAC2FC632551
```

If `s > n/2`, we compute `s' = n - s` to ensure the signature is in canonical form.

#### 4. WebAuthn Signature Construction

WebAuthn doesn't sign the message directly. It constructs a composite hash:

```
1. authenticatorData = device + flags + counter (37+ bytes)
2. clientDataJSON = { type, challenge, origin, ... }
3. clientDataHash = SHA-256(clientDataJSON)
4. signedData = authenticatorData || clientDataHash
5. actualHash = SHA-256(signedData)  ← This is what P-256 signs
```

`W3pkAccount` rebuilds `SHA-256(authenticatorData ‖ SHA-256(clientDataJSON))` onchain and checks that `clientDataJSON` holds `"type":"webauthn.get"` and the expected challenge, at the indices the signature gives.

## PRIMARY Smart Account

[`contracts/`](../contracts) holds the ERC-4337 account a `PRIMARY` passkey owns, built on OpenZeppelin 5.7.0.

- **`W3pkAccount`**: `Account`, `AccountERC7579Hooked`, `SignerWebAuthn` and `ERC7739`. User operations and ERC-1271 signatures are WebAuthn assertions over the hash: `type` is `webauthn.get`, the challenge is the hash, UP and UV are set and `s` is low. ERC-1271 goes through ERC-7739, so a signature for one account can't be replayed on another account owned by the same passkey. ERC-7579 validator, executor, fallback and hook modules can be installed; a hook sees every execution, which is where spending policies plug in. The account isn't upgradeable.
- **`W3pkAccountFactory`**: deploys each account as an ERC-1167 clone and initializes it with the key in the same call. The CREATE2 salt is `keccak256(abi.encode(x, y, keccak256(bytes(tag))))`, with `tag` `"MAIN"` by default, so no other key can be deployed at that address.

The factory is deployed through the deterministic deployment proxy (`0x4e59b44847b379578588920cA78FbF26c0B4956C`, salt 1) and deploys the implementation in its constructor, so both, and every account, have the same addresses on every chain.

Each tag gives its own account, but the accounts of one passkey are linkable onchain through their shared owner.

### Not upgradeable

`W3pkAccount` has no proxy, no `upgradeTo` and no admin, and each clone delegates to a fixed implementation; the OpenZeppelin `…Upgradeable` bases are there for the clones' initializer, not for upgrades. Nobody, w3hc included, can change the code that holds a `PRIMARY` account's funds: an upgrade key would be one key over every account, worth more to steal than any single passkey, and the address would no longer tell what code runs behind it. The cost is that a bug can't be patched in place. A fixed version is a new factory, at new addresses, and users move their funds to it. New behavior that doesn't need new account code comes as ERC-7579 modules, which only the account itself can install, through a UserOperation the passkey signs. An installed validator or executor can act for the account, so a module is trusted like the passkey.

### Trust models

| | `STRICT`, `STANDARD`, `YOLO` | `PRIMARY` |
|---|---|---|
| **Key** | secp256k1 keys derived from the BIP-39 mnemonic, which the SDK decrypts in the page | the passkey's P-256 key, which never leaves the authenticator or the passkey provider |
| **Account** | EOA: no contract to trust | `W3pkAccount`: its code, OpenZeppelin's, the EntryPoint v0.9 and the P-256 verifier (the EIP-7951 precompile, or OpenZeppelin's Solidity verifier) |
| **Who can spend** | whoever holds the mnemonic, a decrypted backup or, in `YOLO`, the exported key | whoever can get a user-verified assertion from the passkey |
| **During a session** | code on the page can sign with the cached mnemonic without a prompt (not in `STRICT`) | every signature asks for a fresh user-verified assertion |
| **Sending** | the SDK signs and sends a transaction | a bundler includes the UserOperation; it can delay or drop it, not alter it |
| **Recovery** | encrypted backups and social recovery restore the mnemonic | the passkey provider's sync (iCloud Keychain, Google Password Manager, a password manager); a lost, unsynced passkey loses the account unless a recovery module is installed |

`PRIMARY` trades the mnemonic, which the page holds in memory and backups carry, for a key nobody can export and contract code nobody can change. A synced passkey is as safe as the provider account it syncs through.

### STANDARD and PRIMARY features

| Feature | `STANDARD` (and `STRICT`, `YOLO`) | `PRIMARY` |
|---|---|---|
| Address | EOA | P-256 smart account, same on every chain |
| `signMessage()` EIP-191, SIWE, EIP-712 | ECDSA (secp256k1) | ERC-7739 / EIP-1271, ERC-6492 before deployment |
| `signMessage()` `rawHash` | yes | no: it would skip ERC-7739's replay protection |
| `sendTransaction()` | EOA transaction, one at a time | ERC-4337 UserOperation, batches, paymasters |
| `signAuthorization()` (EIP-7702) | yes | no: there is no secp256k1 key to delegate |
| Stealth addresses (ERC-5564) | yes | no |
| ML-KEM encryption | yes | no |
| Semaphore and ZK proofs | yes | no |

Stealth addresses, ML-KEM and Semaphore/ZK compute with a secret in the page's memory: the stealth spending and viewing keys and the ML-KEM keys come from the mnemonic, the Semaphore and ZK secrets from the passkey's PRF output, and a Groth16 witness needs the secret itself. An authenticator only signs WebAuthn challenges with its P-256 key, so that key can't do ERC-5564's secp256k1 arithmetic, decapsulate ML-KEM or feed a witness. Running these features as `PRIMARY` would mean a second secret outside the authenticator, the trust model `PRIMARY` drops, so they stay on the `STANDARD` side (`STRICT` and `YOLO` included; Semaphore and ZK take no mode), next to the `PRIMARY` account of the same passkey.

## Signing Messages

`signMessage(message, { mode: 'PRIMARY' })` signs as the passkey's account for the tag. Each call prompts for a fresh user-verified assertion.

| Method | Signed as | `isValidSignature` hash |
|---|---|---|
| `EIP191` | ERC-7739 `PersonalSign` | `hashMessage(message)` |
| `SIWE` | ERC-7739 `PersonalSign` | `hashMessage(message)` |
| `EIP712` | ERC-7739 `TypedDataSign`, packed with the app's domain separator, the contents hash and type | the EIP-712 hash |
| `rawHash` | throws | |

ERC-7739 nests the hash under the account's EIP-712 domain (`W3pkAccount`, `1`, chain, account), so a signature doesn't verify on another chain or another account of the same passkey. The chain is `options.chainId`, required for EIP-191; SIWE reads the message's `Chain ID`, EIP-712 the domain's `chainId`. A bare hash (`rawHash`) would skip that nesting, so PRIMARY mode refuses it.

Unless `eth_getCode` on `options.rpcUrl`, or the first `rpcUrls` endpoint for the chain, shows the account deployed, the signature is wrapped as [ERC-6492](https://eips.ethereum.org/EIPS/eip-6492) with the factory's `createAccount(x, y, tag)` calldata, so verifiers can check it before the account exists.

### Verifying

viem verifies EOA, ERC-1271 and ERC-6492 signatures with the same call:

```typescript
import { createPublicClient, http } from 'viem'
import { mainnet } from 'viem/chains'

const client = createPublicClient({ chain: mainnet, transport: http() })

const { signature, address } = await w3pk.signMessage('Hello World', { mode: 'PRIMARY', chainId: 1 })
const valid = await client.verifyMessage({ address, message: 'Hello World', signature })
```

Onchain, call `IERC1271(account).isValidSignature(hash, signature)` with a bare signature, from a deployed account, and expect `0x1626ba7e`.

## Sending Transactions

`sendTransaction(tx, { mode: 'PRIMARY' })` sends from the passkey's account as one EntryPoint v0.9 UserOperation, through the bundler set in `bundlerUrls` (or `options.bundlerUrl`):

- **Calldata**: ERC-7579 `execute(mode, executionCalldata)`, single mode for one transaction, batch mode for an array, which reverts as a whole if one call reverts
- **Deployment**: when the account has no code on the chain, `factory` and `factoryData` (`createAccount(x, y, tag)`) deploy it in the same UserOperation
- **Nonce**: `EntryPoint.getNonce(account, 0)`; nonce key 0 selects no validator module, so the account checks the passkey signature
- **Signature**: one WebAuthn assertion with the userOpHash as challenge, encoded as for ERC-1271. The SDK computes the userOpHash offchain as `EntryPoint.getUserOpHash` does: the EIP-712 hash of the packed UserOperation, domain `ERC4337`, version `1`, the chain and the EntryPoint, leaving out a trailing paymaster signature
- **Gas**: estimated by the bundler with a stub signature. The stub fails the challenge check before P-256 verification runs, so the SDK adds 15,000 gas to `verificationGasLimit` on chains with the EIP-7951 precompile and 300,000 on chains without it, where OpenZeppelin's Solidity verifier runs
- **Paymaster**: with `paymasterUrl`, an ERC-7677 service supplies `paymaster` and `paymasterData`; otherwise the account pays
- **Result**: the hash of the transaction that included the UserOperation, from `eth_getUserOperationReceipt`, and its `userOpHash`

[`contracts/test/W3pkAccountUserOp.t.sol`](../contracts/test/W3pkAccountUserOp.t.sol) runs SDK-made UserOperations, from fixtures that `scripts/gen-userop-fixtures.ts` writes, through the EntryPoint v0.9 runtime code: their hash is the EntryPoint's, the first one deploys the account, and batches are atomic.

## Security Considerations

### 1. Signature Malleability

w3pk automatically applies low-s normalization using the P-256 curve order to prevent signature malleability:

```typescript
const n = BigInt('0xFFFFFFFF00000000FFFFFFFFFFFFFFFFBCE6FAADA7179E84F3B9CAC2FC632551')

if (s > n / 2n) {
  s = n - s  // Normalize to low-s
}
```

### 2. Origin Binding

WebAuthn signatures are bound to the origin (RP ID). The signature includes:
- `rpIdHash` - SHA-256 hash of the RP ID (domain)
- Prevents cross-origin signature replay

Smart contracts should verify the origin matches expected values.

### 3. Counter Validation

WebAuthn includes a signature counter that increments with each use. This prevents:
- Credential cloning
- Replay attacks

w3pk tracks and validates signature counters in credential storage.

### 4. Hardware Security

P-256 passkeys are typically stored in:
- iOS/macOS: Secure Enclave
- Android: Titan M / StrongBox
- Windows: TPM 2.0

Private keys never leave the secure hardware.
